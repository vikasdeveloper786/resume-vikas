Frontend architecture

How I set an app up so it stays fast and easy to work on as the team and the features grow.

01Application structure

  • One folder per feature, with clear edges between them
  • Server and client components split on purpose; mutations through Server Actions
  • TypeScript throughout, so mistakes show up before the app runs

02State management

  • Server data and screen state kept apart — React Query and Zustand
  • Cached per item, so one change does not reload everything
  • Forms on React Hook Form with a single Zod schema

03APIs & data layer

  • One place that handles auth headers, retries and errors
  • Every response checked, so bad data fails early and loudly
  • Suspense and error boundaries per route, with every state designed up front

04Design system & components

  • 40+ shared components teams build with instead of rebuilding
  • Tailwind tokens and Shadcn UI, themed light and dark in one place
  • Documented in Storybook, with tests and accessibility checks

05Build & tooling

  • Vite, or Turbopack / Webpack where Next.js needs it
  • Bundle analysed per route, so I split where it actually matters
  • Turborepo monorepo, plus SEO metadata, sitemaps and structured data

01How I measure

  • Field Core Web Vitals (LCP, INP, CLS) via the web-vitals library and RUM — real devices and networks, not just a lab run
  • Lighthouse CI budgets wired into the pipeline so a performance regression fails the build
  • React Profiler passes to locate wasted re-renders and expensive commits

02How I optimise

  • Route-level code splitting, dynamic imports and swapping heavy dependencies for lighter equivalents
  • Server Components, SSR / ISR and edge caching to cut client JavaScript and TTFB
  • Image and font discipline — next/image, responsive srcset, AVIF / WebP, subsetting and font-display: swap
  • Render-path work: memoisation where it pays, virtualised long lists, debounced handlers, deferred third-party scripts

Backend & data

The server-side work I own alongside the frontend — the APIs, the database behind them, and what keeps it quick under load.

01API design

Node.jsExpressRESTGraphQLOpenAPI
  • Endpoints designed around resources and clear status codes, not one-off verbs
  • Versioned, so old clients keep working when the shape changes
  • Paginated by cursor on anything that grows, with sensible limits
  • Writes made idempotent, so a retry never creates the same thing twice
  • Documented in OpenAPI, which also generates the client types

02Databases

PostgreSQLMongoDBMySQLPrisma
  • Schema designed first — normalised, with real foreign keys
  • Indexes chosen from the queries that actually run, then checked with EXPLAIN
  • N+1 queries found and fixed with joins or batched loads
  • Changes ship as versioned migrations — reversible, and run in CI
  • Transactions where data must move together, so half-finished writes cannot happen

  • Audit logging, so every model action is traceable

Case studies

Three problems I was handed, what I changed, and what it moved.

CASE 01

Large React application architecture

React · TypeScript · React Query ~120 screens · 4 squads
The problem
  • Four squads shared one codebase with no agreed structure
  • The same data was stored in three places at once, and the copies drifted apart
  • Every release broke screens nobody had touched
  • UI was rebuilt from scratch on each screen instead of reused
What I did
  • Split the app into feature slices with explicit public APIs
  • Moved server data to React Query, UI state to Zustand
  • Put every request behind one typed API layer with checked responses
  • Built a shared component library and review rules to keep it used
Regressions down ~35% 40+ shared components Onboarding time roughly halved
CASE 02

Next.js performance optimisation

Next.js · Core Web Vitals · Lighthouse CI
The problem
  • The main content took 3.8 seconds to appear on a normal phone
  • Chart and date libraries loaded on pages that never used them
  • Images and fonts had no reserved space, so the layout jumped while loading
  • Nothing caught it when a change made the site slower
What I did
  • Moved data-heavy routes to Server Components with ISR
  • Split the bundle per route and replaced the heaviest libraries
  • Fixed images and fonts — next/image, AVIF, subsetting, reserved space
  • Added Lighthouse CI budgets so a slow change fails the build
LCP 3.8s → 1.9s Bundle −42% CLS < 0.05 Lighthouse 95+
CASE 03

AI-powered application

LLM · RAG · Agents · MCP
The problem
  • Users needed answers from their own documents, not general knowledge
  • The model made things up and showed no sources to check
  • There was no safe way to let it change anything in internal systems
  • Every answer went through the strongest, most expensive model
What I did
  • Built a RAG pipeline that returns answers with citations
  • Stored embeddings in Postgres with pgvector, searched vector + keyword
  • Added a tool-calling agent that asks for approval before any write
  • Routed simple questions to a cheaper, faster model
Human approval on writes Token cost down ~60%
